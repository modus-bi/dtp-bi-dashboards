Этап A дал нам понимание данных. Теперь конвертируем находки в исполняемые SQL-проверки. Каждая проверка = одна INSERT в mos.dq_snapshots. Дашборд просто читает этот результат.

Структура таблицы

CREATE TABLE mos.dq_snapshots (
  snapshot_id   bigserial PRIMARY KEY,
  run_at        timestamptz DEFAULT now(),
  rule_id       text NOT NULL,           -- 'DQM-C01-address-not-empty'
  rule_type     text NOT NULL,           -- NOT_NULL_OR_EMPTY / FORMAT / RANGE / UNIQUE / ...
  table_name    text NOT NULL,
  field_name    text,
  total_rows    bigint NOT NULL,
  violations    bigint NOT NULL,
  violation_pct numeric(5,2) GENERATED ALWAYS AS (
    CASE WHEN total_rows > 0 THEN 100.0 * violations / total_rows ELSE 0 END
  ) STORED,
  severity      text CHECK (severity IN ('CRITICAL','HIGH','MEDIUM','LOW'))
);

Лидеры нарушений

Топ-3 проблемных правила (по абсолютному числу violations):
  1. C05 d_fias_not_null — 115 780 строк (21%) с пустой датой ввода в ФИАС.
  2. C04 p7_street — 63 082 объекта (11.45%) без названия улицы (земельные участки в полях, ОКС с координатами).
  3. C03 n_fias_empty — 12 544 (2.28%) с пустым ФИАС-UUID.
Топ-3 «по % но critical/high severity» (мало violations, но дорого если что):
  1. U02 unom_unique — 99 коллизий идентификатора строения (HIGH).
  2. U04 simple_address_unique — 2 552 строк в exact-dup группах (MEDIUM, но видно невооружённым глазом).
  3. Cn02 building-must-have-kadn — 2 800 ОКС со status='Внесён в ГКН', но без кадастрового номера.

Образец одного правила (V05 d_fias not sentinel)

INSERT INTO mos.dq_snapshots (rule_id, rule_type, table_name, field_name,
                              total_rows, violations, severity)
SELECT 'DQM-V05-dfias-not-sentinel',
       'RANGE',
       'mos.address_reestr',
       'd_fias',
       COUNT(*) FILTER (WHERE d_fias IS NOT NULL),
       COUNT(*) FILTER (WHERE d_fias IS NOT NULL
                          AND (d_fias < '1990-01-01' OR d_fias > '2026-12-31')),
       'MEDIUM'
FROM mos.address_reestr;

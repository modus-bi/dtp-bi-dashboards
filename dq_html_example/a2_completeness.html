Completeness = доля строк, в которых поле фактически заполнено. Важный нюанс: для текстовых полей пустая строка '' ≠ NULL, но семантически тоже «отсутствует». Профилировщик должен учитывать оба случая.

SQL шаблон

-- для text-полей считаем NULL и пустые строки одинаково
COUNT(*) FILTER (WHERE col IS NULL OR col = '')
-- для date/numeric/jsonb — только NULL
COUNT(*) FILTER (WHERE col IS NULL)

🟢 Стабильно полные (≥99%)

21 колонка: address, adm_area, district, global_id, obj_type, status, sostad, unom, vid и др. — заполнены во всех или почти всех записях. Это надёжный «костяк» данных, на который можно опираться при проверках.

Ключевые выводы

1. Половина адресов без кадастра. 48.39% строк имеют пустой kad_n. Это нормально для земельных участков (~46% датасета), но среди зданий (Здание/Сооружение, ~54%) тоже встречаются ОКС без кадастрового номера. Для DQ-проверки нужно условное правило: «kad_n обязателен, если obj_type = 'Здание' и status = 'Внесён в ГКН'».
2. Empty strings ≠ NULL. n_fias имеет 12 544 записи с пустой строкой '', но 0 с NULL. Если использовать только IS NULL в DQ-проверке — пропустим 2.28% missing values. Рекомендация: в правилах completeness для text-полей всегда добавлять OR col = ''.
3. Ровно 12 строк имеют пустой simple_address и пустой on_territory_of_moscow. Это интересный артефакт — нужно проверить, не одни и те же ли это записи (возможно, объекты с битой адресной строкой; проверим в A.6).
4. Геометрии нет в этой загрузке. geo_data, lat/lon, geodata_center — пусты, потому что они приходят из отдельного features-эндпоинта (address_reestr_features_raw, 551 574 строк). Для геопроверок нужен JOIN с этой таблицей.
